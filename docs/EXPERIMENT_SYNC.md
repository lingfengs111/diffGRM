# Multi-machine experiment synchronization

The Git repository is the shared **code and evidence layer**, not a mirror of
the complete training filesystem. Raw datasets, checkpoints, caches, rank
arrays, and logs stay local. Source code, experiment configurations, concise
findings, normalized metrics, and small result JSON files are committed.

## What belongs in Git

- `genrec/`, `scripts/`, `experiments/`, and `tests/`;
- root configuration and handoff documents;
- `docs/` for current protocols and project-level conclusions;
- `experiment_records/incoming/<machine-id>/` for machine-owned status and new
  immutable records;
- `experiment_records/archive/` for reviewed terminal records shared by every
  machine.

Do not commit `runs/`, `saved/`, `data/`, `cache/`, `logs/`, model weights, or
large per-example arrays. `.gitignore` enforces the common cases. A checkpoint
may be named in a record, with size and optionally a SHA-256 digest, without
copying the checkpoint itself.

## Directory ownership and lifecycle

```text
experiment_records/
  incoming/
    primary/       # written only by the original workstation
    gpu-ckpt/      # written only by the checkpoint-capable server
    gpu-git/       # written only by the GitHub-only server
  archive/         # shared, reviewed, terminal records
  INDEX.md         # regenerated by the integration/archive step
```

The names above are recommended stable IDs, not mandatory hostnames. Configure
one ID once per clone:

```bash
git config --local diffgrm.machine gpu-ckpt
git config --get diffgrm.machine
```

`record_experiment.py` reads this setting and writes only below that machine's
incoming directory. A machine can maintain its own `STATUS.md` there for its
running queue and local checkpoint availability. Never edit another machine's
incoming directory.

Terminal records (`complete`, `failed`, or `invalid`) are promoted into the
shared archive only after their producer branch is reviewed/merged. Planned or
running records stay machine-owned. Routine producer commits do not edit
`archive/`, `INDEX.md`, or the project-wide current-status document; this keeps
parallel Git merges predictable.

## Record contract

Each record directory contains:

- `manifest.json`: identity, status, dataset, protocol, source paths, Git state,
  producer identity, and hashes of copied evidence;
- `metrics.json`: normalized rows used to build the common index;
- optional `summary.md`: interpretation, validity qualifications, and next
  decision when a run changes the research conclusion;
- optional small files under `artifacts/`, such as the original `result.json`,
  exact command, resolved config, or statistical report.

For an ordinary additional seed or routine control, `manifest.json` plus
`metrics.json` and any essential small raw result are enough. Do not manufacture
a new prose summary for every run. Write one when a suite closes, a protocol or
validity issue needs explanation, or the project-level conclusion changes.

Statuses are `planned`, `running`, `complete`, `failed`, or `invalid`. Never
silently replace an invalid result with a rerun: retain the invalid record and
give the valid rerun a distinct ID. A record is a snapshot. Prefer the
machine-owned `STATUS.md` for frequently changing liveness information and
create the immutable record when the run reaches a meaningful checkpoint.

Use a globally unique ID such as
`20260910_video23_rank32_gpu_ckpt_seed2026`. The producer directory expresses
ownership; retaining a short producer tag in the ID still makes copied links
self-describing.

Create a record with the standard helper:

```bash
python scripts/record_experiment.py \
  --record-id 20260910_video23_rank32_gpu_ckpt_seed2026 \
  --title "Video23 rank-32 listwise, seed 2026" \
  --status complete \
  --dataset Video23 \
  --tag rank32 \
  --summary runs/example/FINAL_FINDINGS.md \
  --metrics runs/example/metrics_for_record.json \
  --artifact result.json=runs/example/result.json \
  --config train.yaml=experiments/example/train.yaml \
  --checkpoint runs/example/best.pt
```

This creates
`experiment_records/incoming/<configured-machine-id>/<record-id>/`.
`metrics_for_record.json` follows the schema documented in
`experiment_records/README.md`. The helper refuses large artifacts and model
weight files. It records checkpoints by reference only.

Before a producer commit, run:

```bash
python scripts/record_experiment.py --help
git status --short
```

The integration/archive step promotes a reviewed record and owns the shared
index update:

```bash
python scripts/archive_experiment_records.py \
  --machine-id gpu-ckpt \
  20260910_video23_rank32_gpu_ckpt_seed2026
python scripts/build_results_index.py
python scripts/build_results_index.py --check
git add -A experiment_records
```

## Pulling an existing clone

Both new servers already contain Git clones, so no re-clone or `git init` is
needed. Check which remote points at the private repository, then fast-forward
the local main branch. A normal clone will usually call it `origin`; the
original workstation calls it `research`.

```bash
git remote -v
git switch main
git pull --ff-only origin main
python scripts/show_experiment_updates.py --since ORIG_HEAD
```

On the original workstation, substitute `research` for `origin`. The final
command avoids rescanning the experiment history: it prints only records and
Top-10 metrics added by that pull.

If a server has local commits, uncommitted source edits, or a non-fast-forward
main branch, do not force the pull. Save the work on a machine branch first and
then merge or rebase deliberately.

## Initial GitHub setup (historical)

The original workstation is also connected to the public DiffGRM source. Its
private research remote is deliberately called `research`, leaving `origin`
untouched:

```bash
git remote add research git@github.com:OWNER/PRIVATE_REPO.git
git push -u research main
```

New servers cloned directly from the private repository normally use `origin`
for that same URL; remote names do not need to match across machines.

## Daily producer workflow

Give each experiment a branch prefixed by the machine ID, for example
`gpu-ckpt/tokenizer-controls` and `gpu-git/rank32`. At the start of work, pull
the agreed integration branch and create the machine branch. At the end of a
run, update only that machine's `STATUS.md`, create its incoming record, and
commit the new code/config/machine-owned files. Push the branch and merge
through GitHub or on the designated integration machine. Unchanged historical
files are content-addressed by Git and are not uploaded again.

Avoid having experiment machines push directly to `main`: source-code
conflicts need review. Per-machine incoming directories keep result evidence
independent, while the integration step is the only writer to the shared
archive/index.

To inspect what another machine currently owns without reading the whole
archive:

```bash
python scripts/show_experiment_updates.py --machine gpu-ckpt
python scripts/show_experiment_updates.py --status running
```

Checkpoint transfer is a separate operation (manual copy, `rsync`, or object
storage); verify a shared checkpoint by SHA-256 before resuming or evaluating
it. The GitHub-only machine still sees every archived metric, protocol, small
result artifact, and checkpoint reference.

Do not infer run liveness from a sandboxed `ps` view alone. Prefer a combination
of an advancing `progress.json` or log timestamp, the recorded launcher PID on
the host, and GPU utilization.
